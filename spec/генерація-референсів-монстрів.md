# Генерація референсів монстрів

Інструкція для генерації референс-арту монстрів MyWay власним FLUX-конвеєром
і вбудовування результату у вікі. Прочитавши цей файл (без жодного іншого
контексту) можна пройти всіх 218 монстрів пачками по 10.

Перевірено на трьох монстрах підземелля (проклятий кристалічний
скорпіон-нежить, кабанолюд-вождь, тіньовий некро-ірбіс — рівні 38–40) і на
дев'яти монстрах першої хвилі (заєць…слиз — рівні 1–4); результат схвалено
замовником на `wiki/test.html`. Налаштування нижче — те, що вже дало добрий
збіг зі знайденими референсами; не підбирати заново, якщо результат не
явно гірший.

## 1. Звідки брати опис

Джерело істини — `spec/бестіарій.json` (масив із 218 об'єктів). У кожного
запису є:

- `назва` — точна українська назва, **використовується як ім'я файла**
  (нижче, розділ 4) — копіювати символ у символ, з апострофами й дефісами.
- `рівень` — число.
- `конвеєр` — літера архетипу тіла: `Л` людиноподібний, `Ч` чотирилапий
  звір, `С` членистоногий, `К` конструкт. Підказка для анатомії, не більше:
  сам опис нижче вже описує тіло повністю.
- `де` — де спавниться (`"зона N"` — поверхня, денне світло; `"підземелля
  N"` — підземелля, темрява). Визначає освітлення й настрій промта
  (розділ 3).
- `опис` — одна фраза-характеристика (напр. «панцир проріс проклятою
  темною рудою»). Використовувати як стрижень образу.
- `опис моделі` — словник із шістьма частинами тіла + тактикою:
  `голова`, `тулуб`, `кінцівки`, `хвіст`, `амуніція`, `зброя`, `тактика`.
  Кожне поле — готове речення українською. Якщо поле порожнє або
  `"Немає"` — просто не писати відповідний рядок промта, а не вигадувати
  «немає X» (крім випадків, де відсутність — сама по собі візуальна
  риса, як у слизу без голови).

Грейд (E–SS) не рахувати вручну — просто взяти вже готовий бейдж
`<span class="g g-X">X</span>` із `wiki/monstry-vyglyad.html` навпроти
картки монстра (`<article class="card" id="mN">`), або порахувати за
рівнем через ту саму драбину, що й `tools/koval.py` (`речі.json →
"грейди" → "до рівня"`) — перше швидше й без ризику розсинхрону.

**Увага — порядок карток НЕ збігається з порядком бестіарію.** Перевірено
на 120 монстрах: `id="m1"` у `monstry-vyglyad.html` — це «вовк» (рівень 2),
а перший запис `бестіарій.json` — «щуролюд-ватажок» (рівень 27). Обидва
джерела містять ті самі 218 імен, але в різному порядку. Крім того, самі
картки фізично розкидані по HTML-файлу не за зростанням номера. Робочий
спосіб різати на пачки:

1. Витягнути з HTML усі пари `id="m(\d+)"` + назва монстра, розкодувавши
   HTML-сутності в назві (наприклад `&#x27;` → апостроф).
2. Відсортувати пари за числом з `id`, узяти наступні 10 за цим порядком
   (m1–m10, m11–m20, …) — це і є номер пачки, а не порядок появи в файлі.
3. Для кожної картки знайти повний опис у `бестіарій.json` **пошуком за
   точним співпадінням назви**, не за індексом масиву. На 120 монстрах
   збіг за назвою був стовідсотковий.

Грейд (E–SS) — читати напряму з бейджа `<span class="g g-X">X</span>`
навпроти картки. Це основний і єдиний потрібний спосіб (підтверджено на
120 монстрах без жодного збою) — драбина через `речі.json → "грейди" →
"до рівня"` (як у `tools/koval.py`) лишається лише теоретичним запасним
варіантом, до якого жодного разу не довелось вдаватись.

## 2. Як формулювати промт

Промт — англійською (FLUX слухається англійської надійніше), один
абзац без переносів рядків між частинами тіла (крапка й одразу наступна
частина — так, як у трьох перевірених прикладах). Шаблон:

```
Dark fantasy RPG monster concept art, full-body portrait of a level {рівень}
{грейд}-rank {англійська назва} ({коротка суть з поля "опис"}), viewed from
a dynamic three-quarter angle, body turned slightly away from camera, not a
head-on frontal pose, {середовище: див. нижче}.Head[/Head and jaws]: {переклад
поля "голова"}.Body[/Body and texture]: {переклад поля "тулуб"}.Limbs: {переклад
поля "кінцівки"}.Tail: {переклад поля "хвіст", якщо є}.Equipment: {переклад поля
"амуніція", якщо є}.Weapon: {переклад поля "зброя", якщо є}.Atmosphere: {освітлення
+ рендер-хвіст}.
```

Правила перекладу й складання:

- **Ракурс — обов'язковий рядок** у кожному промті: `viewed from a dynamic
  three-quarter angle, body turned slightly away from camera, not a
  head-on frontal pose`. Без нього FLUX стабільно тягне до симетричного
  фасу. Хороший приклад того, що вийшло — `skorpion_nezhyt_v2` (seed
  3002): тулуб і хвіст по діагоналі, а не дзеркально симетрично.
- **Англійська назва** — не буквальний переклад, а впізнаваний
  описовий ярлик (як «Shadow Necro-Irbis», «Boar-man Chieftain», а для
  простих звірів просто «hare», «wolf», «desert snake»). Тримати той
  самий ярлик для обох варіантів (v1/v2) одного монстра.
- **Переклад частин тіла** — перекладати опис максимально буквально,
  зберігаючи всі конкретні деталі (матеріали, кольори, кількість,
  текстури). Нічого не додавати від себе понад те, що написано в
  `опис моделі`; нічого важливого не викидати.
- **Тактику (`тактика`)** у промт не тягнути як окремий рядок — вона
  для гри, не для пози; коротку суть із неї можна вплести в `Atmosphere`
  або в дужки після назви, якщо це щось видиме (наприклад «partially
  materializing out of darkness»).
- **Середовище й освітлення** — брати з поля `де`, не вигадувати:
  - `"зона N"` (поверхня) → денне світло, трава/рівнина/пустеля/крига
    відповідно до типу монстра, `cinematic lighting`, реалістичні
    текстури хутра/шкіри/луски.
  - `"підземелля N"` → темне підземелля, low-key освітлення, контраст,
    частки пилу/темряви/кристалів — залежно від опису.
  - Якщо в `опис`/`опис моделі` є прокляття/нежить/тінь/кристали —
    підсилити відповідними частками й кольором світіння (як у трьох
    перевірених прикладах — фіолетово-чорні кристали, бліді вогники
    тощо), а не додавати генеричний «dark fantasy» без підстави в тексті.
  - Завжди закривати рядком рендер-стилю: `high detail texture, 8k
    resolution, Unreal Engine 5 style rendering` (або `render style` —
    без різниці, обидва варіанти зустрічались і працюють однаково).
  - Поле `де` часто дорівнює `"у грі"` — це **типовий випадок для більшості
    монстрів 1–2 хвилі, не рідкісний виняток**, і спека раніше цього не
    покривала. У такому разі середовище й освітлення не з поля `де`, а
    вигадується за типом істоти й описом (лісова галявина для зайця,
    печера для кажана тощо) — так само як для `"зона N"`/`"підземелля N"`,
    просто без прив'язки до конкретного номера зони.

### Нюанси, підтверджені на 120+ монстрах (пачки 1–13)

FLUX стабільно провалює певні класи запитів навіть при точному
дотриманні шаблону вище. Перегенерація одного монстра з двома новими
seed коштує дешево (3–8 хв на 2–4 зображення) — плановано закладати її
на такі випадки, а не сподіватись на перший прогін:

- **Зайва/незвична кількість частин тіла** (4 роги, 4 ока, 4 руки, 2
  голови, 3 хвости) — найненадійніша категорія. FLUX тягне до анатомічної
  норми навіть з підсиленим формулюванням («FOUR HORNS total») —
  повторний прогін іноді все одно повертає стандартну кількість.
  Плюс до посиленого позитиву обов'язково додавати негативний промт
  (див. розділ 4 про поле `negative`) з протилежним терміном, наприклад
  `two horns, single head` для дворогого/двоголового монстра.
- **Кінцівки там, де їх не повинно бути** (слиз без кінцівок, змії,
  наги) — лікується негативним промтом `legs, arms, limbs, hands, claws,
  feet`. Для чистих змій/слизів спрацьовує майже завжди; для гібридів
  людина+змія (наги) — лише частково навіть після редо, приймати
  результат «краще з двох», а не гнатись за ідеалом.
- **Примарність/дим/прозорість** не досягається описом кольору
  («чорна шерсть», «темний дим») — потрібні прямі слова `translucent,
  ghostly, see-through, silhouette made of smoke, paws hovering above
  ground fading into mist` у позитиві й `opaque, solid fur,
  photorealistic animal` у негативі. Застосовувати проактивно до будь-
  якого монстра з «тінь»/«примара»/«привид» в описі, не чекаючи
  невдалого першого прогону.
- **Фронтальна поза просочується** в ~20–30% генерацій навіть з
  обов'язковим рядком ракурсу — особливо в кажанів/сов (симетрично
  розкриті крила) і гуманоїдних боссів. Для кажанів/сов проактивно
  додавати конкретну позу: `clinging to a wall/ceiling/branch, asymmetric
  wing pose` у позитив і `symmetric, front view, wings spread evenly` у
  негатив.
- **Оголеність**: будь-який жіночий/умовно-гуманоїдний монстр провокує
  неприпустиму оголеність в обох варіантах з першого разу, навіть якщо в
  описі про це немає ні слова. Проактивно додавати `fully clothed,
  modest attire, tasteful [опис одягу з амуніції]` у позитив і nsfw-
  терміни в негатив — не чекати поганого результату.
- **Водяні знаки/сторонні об'єкти на фоні**: приблизно в 1 з 40–50
  зображень трапляється сторонній текст або об'єкт без видимого тригера
  в промті — не промт-проблема, а причина перевірити ОБИДВА варіанти на
  це при відборі (розділ 5) і просто взяти інший, якщо один зіпсований.

## 3. Розмір кадру — критично для того, як фото ляже у вікі

`wiki/monstry-vyglyad.html` показує фото у квадратній рамці з
`object-fit: cover` (`.photo{aspect-ratio:1/1}`, обрізає, а не
вписує!). Тому **фінальні зображення для вікі генерувати квадратними,
1024×1024**, з запасом по краях (істота не впритул до країв кадру) —
інакше кадрування обріже лапи, зброю чи хвіст. Портрет 896×1152, яким
робились перші тести на `test.html` (там `object-fit: contain`, без
обрізання), для фінального фото в `monstry-vyglyad.html` не годиться
без додаткового кадрування.

## 4. Якими інструментами

Локальний ComfyUI + FLUX (той самий конвеєр, що для мап і значків
речей). Моделі вже стоять:

- unet: `flux1-dev-Q4_K_S.gguf` (GGUF, вузол `UnetLoaderGGUF`)
- clip: `t5xxl_fp8_e4m3fn.safetensors` + `clip_l.safetensors`
  (`DualCLIPLoader`, `type: flux`)
- vae: `ae.safetensors`

Запуск сервера (якщо не піднятий):

```bash
cd ~/ComfyUI && source venv/bin/activate
nohup python main.py --listen 127.0.0.1 --port 8188 > /tmp/comfyui.log 2>&1 &
disown
# зачекати й перевірити:
curl -s http://127.0.0.1:8188/system_stats
```

Генерація — через HTTP API (`POST /prompt`, потім опитувати
`/history/{prompt_id}`), workflow-граф як у `~/map-gen/scripts/gen_map.py`.
Параметри семплінгу, що вже підтверджені (не підбирати заново без
причини): `steps=28, guidance=3.5 (FluxGuidance), cfg=1.0,
sampler_name="euler", scheduler="beta", denoise=1.0`, розмір `W=H=1024`
для фінальних фото (розділ 3).

Робочий скрипт (підставити свій список монстрів пачкою до 10, seed —
будь-які різні цілі, аби не збігались усередині пачки):

```python
import json, time, urllib.request, uuid

SRV = "http://127.0.0.1:8188"
W, H, STEPS, GUID = 1024, 1024, 28, 3.5

MONSTERS = [
    # (тимчасове латинське ім'я файла, повний англійський промт, [seed_v1, seed_v2], negative_prompt)
    # negative_prompt = "" для звичайного випадку; заповнювати конкретними
    # термінами для класів проблем із розділу 2 ("Нюанси, підтверджені...")
    ("zayets", "Dark fantasy RPG monster concept art, ...", [101, 102], ""),
]

def wf(prompt, seed, prefix, negative=""):
    return {
      "1": {"class_type": "UnetLoaderGGUF", "inputs": {"unet_name": "flux1-dev-Q4_K_S.gguf"}},
      "2": {"class_type": "DualCLIPLoader", "inputs": {"clip_name1": "t5xxl_fp8_e4m3fn.safetensors", "clip_name2": "clip_l.safetensors", "type": "flux"}},
      "3": {"class_type": "CLIPTextEncode", "inputs": {"text": prompt, "clip": ["2", 0]}},
      "7": {"class_type": "CLIPTextEncode", "inputs": {"text": negative, "clip": ["2", 0]}},
      "4": {"class_type": "FluxGuidance", "inputs": {"conditioning": ["3", 0], "guidance": GUID}},
      "5": {"class_type": "EmptySD3LatentImage", "inputs": {"width": W, "height": H, "batch_size": 1}},
      "6": {"class_type": "KSampler", "inputs": {"model": ["1", 0], "positive": ["4", 0], "negative": ["7", 0],
            "latent_image": ["5", 0], "seed": seed, "steps": STEPS, "cfg": 1.0,
            "sampler_name": "euler", "scheduler": "beta", "denoise": 1.0}},
      "8": {"class_type": "VAELoader", "inputs": {"vae_name": "ae.safetensors"}},
      "9": {"class_type": "VAEDecode", "inputs": {"samples": ["6", 0], "vae": ["8", 0]}},
      "10": {"class_type": "SaveImage", "inputs": {"images": ["9", 0], "filename_prefix": prefix}},
    }

def post(path, obj):
    r = urllib.request.Request(SRV + path, data=json.dumps(obj).encode(), headers={"Content-Type": "application/json"})
    return json.load(urllib.request.urlopen(r))

cid = str(uuid.uuid4())
jobs = []
for name, prompt, seeds, negative in MONSTERS:
    for i, s in enumerate(seeds, 1):
        prefix = "%s_v%d" % (name, i)
        pid = post("/prompt", {"prompt": wf(prompt, s, prefix, negative), "client_id": cid})["prompt_id"]
        jobs.append((prefix, pid))

for prefix, pid in jobs:
    while True:
        h = json.load(urllib.request.urlopen(SRV + "/history/" + pid))
        if pid in h:
            imgs = [i["filename"] for o in h[pid]["outputs"].values() for i in o.get("images", [])]
            print("done", prefix, "->", ",".join(imgs), flush=True)
            break
        time.sleep(5)
```

Один прогін кожної версії за замовчуванням; при провалі обох варіантів —
одна точкова перегенерація з новими seed (і, якщо потрібно, з
негативним промтом), а не нескінченні ітерації. ~70–90 с на зображення
на цій GPU (RTX 5060 Ti, 16 ГБ), але **пачка з 10 монстрів по 2 варіанти
реально займає ~45–50 хв**, а не 25–30 (виміряно на пачках 1–13) — тому
за 22 пачки закладати ~15–17 год GPU-часу сумарно, а не ~10. Точкові редо
(2–4 зображення) — дешеві, 3–8 хв. Запускати генерацію у фоні
(`run_in_background`/`nohup`), не чекаючи синхронно.

**Колізії за `filename_prefix` між сесіями.** ComfyUI не перезаписує
файл, а дописує зростаючий числовий суфікс (`_00001_`, `_00002_`, …) до
кожного нового зображення з тим самим префіксом. Якщо в
`~/ComfyUI/output/` вже лежать старі файли з такими самими префіксами
(наприклад, від попередніх тестових прогонів) — новий результат зʼявиться
під **більшим** числовим суфіксом, а не під `_00001_`. Тому при пошуку
готового файлу для монстра завжди брати файл із **найбільшим** числовим
суфіксом на цей префікс, а не перший знайдений.

## 5. Відбір і збереження результату

1. Переглянути обидва варіанти (v1/v2) кожного монстра. Обрати той, що
   краще: (а) відповідає опису анатомії з `бестіарій.json` (кількість
   рук/голів/рогів/очей, наявність чи відсутність кінцівок — типова точка
   провалу, див. розділ 2), (б) знятий під кутом, а не у фас, (в) не
   обрізає ключові деталі при квадратному кадруванні, (г) без стороннього
   тексту/водяного знака чи випадкового об'єкта на фоні (трапляється
   рідко, ~1 з 40–50, без видимого тригера в промті — просто взяти інший
   варіант). Якщо жоден не годиться — перегенерувати цього монстра
   окремо з новими seed (за потреби додавши негативний промт, розділ 4),
   а не тягнути далі невдалий варіант. Якщо й повторний прогін не
   виправив проблему з кількістю частин тіла — прийняти кращий з
   наявних і не гнатись за ідеалом далі другого прогону.
2. Обраний файл скопіювати (не сирий вивід ComfyUI з суфіксом
   `_00001_`, а перейменований) у:

   ```
   wiki/img/monstry/<точна назва з "назва">.png
   ```

   Назва — байт-у-байт як у `бестіарій.json`, з пробілами й дефісами
   (наприклад `тіньовий некро-ірбіс.png`). Розширення `.png`, `.jpg`
   або `.webp` — усі три перевіряються генератором вікі, підійде будь-яке.
3. Перезібрати вікі (**руками `wiki/*.html` не правити** — усе
   перезаписується цим скриптом):

   ```bash
   cd ~/гра-lineage && python3 tools/wiki.py
   ```

   Скрипт сам підхопить нові файли з `wiki/img/monstry/` і вставить їх
   у відповідні картки `monstry-vyglyad.html`; лічильник «Зображень
   зараз: N із 218» на самій сторінці — перевірка, що фото прив'язались.
4. Невикористаний (відхилений) варіант і сирі файли ComfyUI можна не
   зберігати — вони не йдуть у git, лишаються тільки в
   `~/ComfyUI/output/`.
